# ADR-001: Relational data model and hosted Postgres release

- **Status:** Accepted
- **Date:** 2026-09-29 (Week 5 deployment decision; original relational decision dated 2026-09-01)
- **Decision owners:** Internal Operations Service Hub team

## Context

The Service Hub serves Employees, department Staff, and Admins across IT, HR, and Finance. Requests have a requester, department, optional Staff owner, and status history. Employees see their own requests, Staff see their department queue, and Admins need a unified cross-department view. Authorization depends on these relationships and must be enforced by the backend.

The first implementation used SQLite. The hosted web service has ephemeral local storage, so a SQLite database stored with the service could be lost on restart or deploy. The final product must remain usable without the student laptop and preserve request state.

## Decision

Use one relational data model and one logical database. Use hosted Postgres (Neon) in production and SQLite locally and in automated tests. Select Postgres when DATABASE_URL is configured. Keep the normalized entities: User, Department, Request, and Request Status History.

Use TypeORM schema synchronization only to initialize an empty hosted database: enable DB_SYNCHRONIZE, deploy, seed the Staff/Admin profiles, then disable synchronization and redeploy. This repository does not yet provide a migration system. Future schema changes therefore require a planned and documented database change rather than leaving synchronization enabled.

Deploy the NestJS API and React static frontend as a Render Blueprint. Firebase Authentication remains the identity provider; the API verifies Firebase ID tokens and derives role and department from server-side configuration. AI triage remains an optional advisory dependency and never owns request submission or lifecycle decisions.

## Alternatives considered

- **SQLite on the hosted service:** rejected because the service filesystem is ephemeral and request persistence is a hard requirement.
- **Hosted Postgres on the same free host:** rejected for this release because its free database has a short expiry window; Neon is selected for the hosted database.
- **Separate database per department:** rejected because Admins need one combined view and it complicates authorization and aggregation.
- **Document database or multiple services:** rejected because the current domain has stable relational ownership and does not need distributed architecture.
- **Migrations before first deployment:** deferred to keep this release small. This increases the operational risk of future schema changes and is documented in the Week 5 risks.

## Consequences

### Benefits

- Request state survives API restarts and redeployments.
- Relational constraints and queries represent ownership, department isolation, history, and Admin views.
- Local development and automated tests remain simple to start with SQLite.
- A new empty database can be rebuilt from the repository schema setup and seed command.

### Risks and operating controls

- Free-tier service sleep can delay the first request; external liveness monitoring mitigates but does not eliminate this risk.
- Free database limits and suspension policies still apply; keep the database account and recovery procedure documented.
- SQLite integration tests do not substitute for the live Postgres smoke test.
- TypeORM synchronization can alter schema automatically; keep it disabled after initial provisioning and record any schema-change procedure.
- Firebase service credentials and all provider/database secrets must stay in hosting configuration and never in Git or logs.

## Acceptance evidence

The decision is proven in operation only when the deployed health response identifies the submitted SHA, the live UI journey creates and updates a persistent request, the release smoke passes against Postgres, and the fresh-database recovery drill succeeds. Evidence and the GO/NO-GO decision belong in docs/week5-release-operations.md.
